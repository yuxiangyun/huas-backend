# 本服务登录以身份认证为准，学校交互要求仍触发整体重新登录

CAS 明确确认身份后，立即原子提交认证事实并完成本服务登录；学校资料和 Portal/JW 等能力在实际使用时获取，不在登录响应前激活，也不由登录触发后台预热。首次姓名、班级为空不阻止登录，成功响应继续保留 token 和 user 对象。这样学校业务故障不会阻断本来可以使用的本地功能，也消除首次认证后返回失败、再次快捷登录却成功的准入矛盾。

用户已登录后，若学校明确拒绝已保存凭据或要求验证码，保留现有客户端清除整个登录态、要求重新登录的产品行为。网络故障、学校服务异常、未知页面和新会话重放后仍失败均不得冒充这种交互要求；它们应返回学校能力不可用或超时，并保留客户端登录态。这里的整体退出指客户端会话处理，不新增服务端全设备 JWT 撤销机制。

## 取舍

选择按需获取，接受学校功能首次使用时的恢复等待和首次资料暂缺，避免登录路径承担全部学校系统的可用性及后台任务生命周期。没有采用“至少一个学校系统激活后才允许登录”，也没有采用登录后主动预热。

明确交互要求时选择整体重新登录，而非保持社交会话并新增独立学校认证入口；因此必须保留明确拒绝/验证码的证据边界，学校普通故障不得触发同一退出流程。

## 实现边界

已实现于 Identity 与 SchoolAccess。CAS 协议层收到明确成功票据即返回，登录应用层不再激活 Portal/JW 或回填资料。保留真实 CAS 提交不自动重放、epoch/generation 条件提交删除及目标能力隔离规则。
