# 本服务登录以身份认证为准，学校交互要求仍触发整体重新登录

CAS 明确确认身份后，立即原子提交认证事实并完成本服务登录；Portal/JW 业务能力在实际使用时获取，不在登录响应前激活，也不由登录触发通用预热。首次姓名、班级为空不阻止登录，成功响应继续保留 token 和 user 对象，同时发出一次尽力后台资料补全。这样学校业务故障不会阻断本来可以使用的本地功能，也避免用户长期只有学号而资料、后台与日志无法识别。

用户已登录后，若学校明确拒绝已保存凭据或要求验证码，保留现有客户端清除整个登录态、要求重新登录的产品行为。网络故障、学校服务异常、未知页面和新会话重放后仍失败均不得冒充这种交互要求；它们应返回学校能力不可用或超时，并保留客户端登录态。这里的整体退出指客户端会话处理，不新增服务端全设备 JWT 撤销机制。

## 取舍

选择业务能力按需获取，并对缺失资料做定向后台补全；登录响应不等待资料请求，补全失败只记录日志并允许下次登录重试。由此避免登录路径承担学校系统可用性，同时让只使用课表、成绩或校园卡的用户也能最终补齐姓名和班级。没有采用“至少一个学校系统激活后才允许登录”，也没有采用登录后主动预热全部学校能力。

明确交互要求时选择整体重新登录，而非保持社交会话并新增独立学校认证入口；因此必须保留明确拒绝/验证码的证据边界，学校普通故障不得触发同一退出流程。

## 实现边界

已实现于 Identity、SchoolAccess 与 Portal UserService。CAS 协议层收到明确成功票据即返回；登录应用层只经端口请求资料补全，基础设施在后台调用具名 `portal.profile`，缓存命中也会补齐 `users` 的空姓名或班级。保留真实 CAS 提交不自动重放、epoch/generation 条件提交删除及目标能力隔离规则。
